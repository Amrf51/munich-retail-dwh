# Assumptions

Every assumption below was derived from measuring the source file, not from guessing
what retail data usually looks like. Row counts come from
[`profiling_findings.md`](profiling_findings.md), which is regenerated by
`scripts/initial_inspection.py`, and from the loaded warehouse itself.

Source: `munich_retail_sales_raw.csv`, 35,612 rows, 38 columns, transactions dated
2024-10-13 to 2025-05-11.

**The governing principle behind all of them: nothing is deleted to make the numbers
look clean.** Every suspect row is loaded with a bit set in `dq_flags`, and the views
decide what to exclude. Only rows that cannot be typed at all would be quarantined in
`raw.rejects`. On this source, that count is zero.

---

## Structural assumptions

### 1. `invoice_number` is not a basket identifier

This is the assumption that shapes the whole model, so it goes first.

**Evidence.** 29,448 distinct invoice numbers across 35,612 rows. Of the 5,416 that
appear on more than one row:

| Header attribute | Invoices with conflicting values |
|---|---:|
| `transaction_date` | 5,397 (99.6%) |
| `sales_staff_id` | 4,947 (91.3%) |
| `payment_method` | 4,766 (88.0%) |
| `store_id` | 4,509 (83.3%) |
| `customer_id` | 3,261 (60.2%) |

**Assumption.** `invoice_number` is a randomly generated string that collides by
chance. Two rows sharing one are a coincidence, not the same basket. A real invoice
header would show zero conflicts on all five attributes.

**Consequence.** The fact grain is **one row = one sale line**, keyed on
`transaction_id`. `invoice_number` is carried as a degenerate dimension: an attribute
on the fact with no dimension table and no foreign key, because it identifies nothing.
No invoice-header table is built.

**If wrong.** If the source system confirms invoice numbers are meant to be unique per
basket, this is the first thing to revisit — a basket-grain fact would unlock
market-basket analysis. Until then, modelling a hierarchy the data does not support
would produce baskets mixing three stores and four dates.

---

### 2. `transaction_id` is unique but not always a UUID

**Evidence.** 34,923 values are canonical UUIDs. 689 (1.9%) are 10-character
uppercase alphanumeric strings. All 35,612 values are distinct.

**Assumption.** Two id generators fed this extract. Both produce valid, unique keys;
only the format differs.

**Consequence.** `transaction_id` is `TEXT NOT NULL UNIQUE`, not `UUID`. Typing it
`UUID` would have rejected 689 perfectly good rows over a cosmetic difference. Flagged
with bit 512 so the inconsistency stays visible without costing any data.

---

### 3. Three date formats coexist and are mechanically distinguishable

**Evidence.**

| Format | Rows | How it is identified |
|---|---:|---|
| `YYYY-MM-DD` | 33,864 | unambiguous |
| `DD/MM/YYYY` | 877 | slash-separated; first component reaches 31, so day-first |
| `MM-DD-YYYY` | 871 | dash-separated; first component never exceeds 12, second reaches 31, so month-first |

**Assumption.** The separator implies the convention: slash means day-first,
dash-with-four-digit-year means month-first.

**Consequence.** `parse_date` tries formats in a fixed order. **All 35,612 rows parse;
zero remain unparsed.** A `DD.MM.YYYY` branch is included defensively although the
current file contains none.

**Risk.** This is the assumption most likely to be wrong in a way that is invisible.
`04-09-2025` read as month-first gives 9 April; read as day-first it would be
4 September. The evidence is strong — the first component never exceeds 12 across all
871 rows — but a future extract with different data could break the inference. Worth
confirming with the source system rather than relying on inference forever.

## Entity assumptions

### 4. One id with two names is an alias, not two entities

**Evidence.** After case-folding, two genuine conflicts survive:

- `store_id` 1: `Olympia Einkaufszentrum` (5,157 rows) / `OEZ München` (5,102 rows)
- `supplier_id` 1: `DW GmbH` (13,262 rows) / `Deutsche Waren GmbH` (9,108 rows)

Every other attribute of those ids is identical.

**Assumption.** The id is authoritative; the name is the unreliable field.

**Consequence.** Canonical name chosen by majority vote per id, ties broken by the
longer string. Deterministic given the same input, and needs no hand-maintained
mapping table that would rot the moment a new alias appears. Result: 7 store names
collapse to 6, 4 supplier names to 3.

---

### 5. `Copy of ` is a prefix artefact, not part of the product name

**Evidence.** 3,535 rows across exactly 4 `product_id` values carry the prefix. Both
variants map to the same id, and all other product attributes match.

**Consequence.** Prefix stripped, applied repeatedly to handle `Copy of Copy of X`.
50 product names collapse to 46.

---

### 6. Categorical columns suffer casing drift, plus one typo

**Evidence.** `transaction_status` has 9 distinct values collapsing to 3. `store_type`
has 12 collapsing to 4. `payment_method` has 20 collapsing to 5.

**Assumption.** These are the same values with inconsistent casing. One genuine typo:
`Mobil Zahlung` (70 rows) and `Mobile Zahlung` (6,450 rows) are the same payment
method.

**Consequence.** Standardised by explicit lookup rather than a blanket `.title()`,
which would have turned `EC-Karte` into `Ec-Karte`.

---

### 7. Store 6 is a placeholder record with real transactions attached

**Evidence.** 5,154 rows — 14.5% of the file. `store_name` is `Imaginary Store`,
`store_location` is `Nowhere St. 123`, `store_size_sqm` is `-500`, `district_name` is
`Unknown`, `postal_code` is `00000`. But those rows reference all 46 real products,
all 34 real customers and all 10 real staff, and their amounts are ordinary.

**Assumption.** The store master record is fabricated; the transactions are not.

**Consequence.** Facts are **kept**. `dim_store.is_placeholder` is set to true and
`store_size_sqm` is nulled — nulled rather than clamped to zero, because "unknown
area" is honest while "0 sqm" would be a fabricated fact sitting in a dimension
someone might later average. `mart.vw_net_revenue` excludes these rows;
`mart.vw_sales_enriched` keeps them.

**Reasoning.** Deleting 14.5% of a dataset to make it tidy is the wrong default. This
is a documented, reversible exclusion instead.

---

### 8. No slowly changing dimension is needed for this extract

**Evidence.** `product_id` maps to exactly one value of every product attribute,
including `base_price` (46 ids, 46 prices). `customer_id` maps to exactly one
`loyalty_status`, one name and one email. Zero conflicts across the full seven-month
window.

**Assumption.** Attributes are static in this extract.

**Consequence.** `dim_customer` carries SCD Type 2 columns (`valid_from`, `valid_to`,
`is_current`) with open-ended validity, but the loader runs **Type 1**. The structure
is ready so that adding versioning later is a loader change rather than a schema
migration. Building a Type 2 loader today would produce a table where every customer
has exactly one version forever.

## Numeric and monetary assumptions

### 9. `unit_price = base_price × (1 − discount_rate)` is reliable

**Evidence.** Holds within €0.01 for **100.0%** of the 35,491 rows where all three
values parse.

**Consequence.** The price side of every record is treated as trustworthy. This is
what makes assumptions 10, 11 and 12 safe, so it is stated separately rather than
buried inside them.

---

### 10. `discount_rate` outside [0, 1] is the corrupt field, not `unit_price`

**Evidence.** 372 rows have `discount_rate` above 1 (maximum 2.0). All 372
consequently have a negative `unit_price` (minimum −€289.82). `base_price` is never
negative in any row.

**Assumption.** The rate was corrupted and the derived price inherited the corruption,
rather than the price being independently wrong.

**Consequence.** `discount_rate` is nulled, `unit_price` falls back to `base_price`,
and bit 4 is set. **Zero negative unit prices remain after the transform.**

**Reasoning.** Someone has to decide which of the two fields is wrong. `base_price`
being universally non-negative, plus assumption 9 holding at 100%, points at the rate.
The alternative is propagating a negative price into revenue.

---

### 11. `total_amount` is not authoritative; the total is recomputed

**Evidence.** `total_amount = quantity × unit_price` holds for only 97.1% of testable
rows. 1,016 rows disagree beyond a cent, spread across all three statuses — so the
mismatches are not explained by cancellations or returns. `tax_amount` tracks the
(sometimes wrong) total, so it is recomputed too.

**Assumption.** Given assumption 9 holds universally and this identity does not, the
corruption is in `total_amount`.

**Consequence.** `total_amount = quantity × unit_price` is computed and canonical.
`total_amount_raw` preserves what was delivered. Bit 1 is set on rows where they
disagree.

**Note on the count.** 1,378 rows end up flagged rather than 1,016. The extra 362 are
rows whose price was corrected under assumptions 10 and 12, so their recomputed total
now legitimately differs from the delivered one. This is expected, not drift.

---

### 12. `N/A` is a null token, and missing numerics are derivable

**Evidence.** 121 rows have `quantity = "N/A"`, 121 have `unit_price = "N/A"`, 102
have `total_amount = "N/A"`. **No row has more than one**, so each gap has two intact
neighbours and can be filled via the identity in assumption 9.

**Consequence.** Repaired arithmetically and flagged with bit 32. 344 rows affected.

---

### 13. Extreme and negative quantities are suspicious, not invalid

**Evidence.** 164 rows have `quantity > 20`, reaching 9,963 — one line implies
€2.38m. 190 rows have negative quantity, but 176 of those sit on `Completed` lines
rather than `Returned` ones.

**Assumption.** Injected noise, but not confidently separable from genuine bulk orders
and mis-statused returns.

**Consequence.** Kept and flagged (bits 2 and 8), excluded from `vw_net_revenue`. The
threshold is configurable via `QUANTITY_OUTLIER_THRESHOLD` rather than hardcoded,
because it is a judgement call rather than a fact.

---

### 14. `tax_rate` is a constant 19%

**Evidence.** Exactly one distinct value across all 35,612 rows: `0.19`.

---

### 15. `discount_applied` is unreliable and derivable

**Evidence.** 1,756 rows null. 257 rows say `False` while `discount_rate > 0`.

**Consequence.** The column is not carried into the mart. Discount presence is derived
from `discount_rate`. Contradictions are flagged with bit 128 (105 rows survive to the
mart, the rest having had their rate nulled under assumption 10 first).

---

## Completeness assumptions

### 16. A missing `customer_id` means a walk-in, not a data error

**Evidence.** 8,380 rows (23.5%) have no `customer_id`. Separately, 1,257 rows carry a
loyalty status with no customer id, and 2,478 carry a customer id with no loyalty
status.

**Consequence.** Routed to the `customer_key = -1` Walk-in member, so the fact table
keeps a `NOT NULL` foreign key and walk-in becomes a queryable segment rather than an
absence. Flagged with bit 64, which is informational rather than a defect.

---

### 17. A missing promotion means no promotion

**Evidence.** 26,741 rows (75.1%) have no `promotion_id`. Promotion and discount are
independent: 6,106 rows have a promotion with no discount, 8,131 have a discount with
no promotion.

**Consequence.** `promotion_name` is a degenerate column on the fact; nulls mean no
promotion. Promotions are explicitly **not** treated as the cause of discounts.

---

### 18. `product_department` is missing only for the `Miscellaneous` category

**Evidence.** All 3,393 null departments belong to `product_category = Miscellaneous`
(of 4,083 such rows).

**Assumption.** Structurally unassigned rather than randomly lost.

**Consequence.** Defaulted to `'Unassigned'` rather than left null, so department
roll-ups stay complete instead of silently dropping 9.5% of rows.

---

### 19. Cancelled and returned lines are kept, not filtered

**Evidence.** After standardisation: 33,446 Completed, 1,089 Canceled, 1,077 Returned.

**Consequence.** `vw_sales_enriched` computes `is_revenue_recognized` as
`transaction_status = 'Completed'`. `mart.vw_net_revenue` respects it;
`mart.vw_returns_and_cancellations` exposes the rest.

**Reasoning.** Deleting them at load would make return-rate analysis permanently
impossible. Ignoring the distinction would inflate revenue. A computed flag in one
view declares the rule once rather than repeating it in every query.

---

### 20. 2,367 email addresses cannot be parsed into a domain

**Evidence.** 27,171 non-null addresses. 24,804 contain exactly one `@`. 2,367 contain
`#` where the separator should be, across 3 distinct values.

**Consequence.** `email_domain` is null for those rows, flagged with bit 1024. It is
never guessed.

**Why this matters beyond data quality.** Splitting on `@` and taking the last part
returns the *whole string* when there is no `@` — which would put a local part, in
other words a person's name, into the mart. The domain extractor validates the
separator before splitting. This was found the hard way: the first version of the
profiling script printed those values into a report destined for version control.

## What the assumptions cost

Excluding flagged rows is not free, and the size of the effect is worth stating
plainly rather than leaving a reader to discover it:

| Scope | Lines | Revenue |
|---|---:|---:|
| All revenue-recognised lines | 33,446 | €138,396,539.72 |
| `mart.vw_net_revenue` (flagged excluded) | 27,368 | €6,682,672.44 |

The €131.7m difference is almost entirely the 165 quantity outliers; a single line of
9,963 units contributes €2.38m by itself. Reporting on the unfiltered figure would be
meaningless.

This is the strongest argument for flagging rather than trusting, and it is why
`mart.vw_net_revenue` rather than `mart.fact_sales` is the documented entry point for
reporting.

## Assumptions I would most want to verify with the source system

Ranked by how much damage a wrong answer would do:

1. **The date format inference (3).** Wrong here means silently wrong dates on 871
   rows, which no downstream check would catch.
2. **The invoice-number finding (1).** It determines the grain. If those collisions
   are a bug rather than a design, the whole model changes shape.
3. **Which of `total_amount` and `quantity` is corrupt (11).** The evidence points at
   the total, but the alternative reading — that quantity is corrupt and the total is
   right — is not impossible.
4. **Whether store 6 should exist at all (7).** 14.5% of the data hangs on this being
   a placeholder master record rather than a test store whose transactions are also
   synthetic.
